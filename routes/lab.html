Laboratory Extension Case Study

How an unmanaged extension became a security problem

1. Business requirement introduced Laboratory staff requested faster access to patient laboratory results.
2. Security requirements omitted The extension was developed without a formal threat model, security acceptance criteria or dedicated architecture review.
3. Independent implementation The laboratory team used its own authentication assumptions and data-access conventions.
4. Direct production deployment The extension was deployed without documented security testing, dependency inventory or formal production approval.
5. Extension becomes forgotten Because ownership and documentation were unclear, the component was missed by later vulnerability and patch-management activities.
6. Security weakness discovered Beta testing later identifies inconsistent authorization between the laboratory extension and the core patient module.
7. H.A.W.K.S. remediation The replacement introduces centralized identity, server-side authorization, input validation, controlled APIs, audit logging and Secure SDLC approval gates.
